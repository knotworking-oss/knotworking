# Notifications

Members get an **Inbox** entry (and an unread badge in the sidebar) when work lands on them:

| Type                  | Created when                                                                         | Recipient        |
| --------------------- | ------------------------------------------------------------------------------------ | ---------------- |
| `task_assigned`       | A task is created with an assignee, or its assignee changes                          | The new assignee |
| `task_status_changed` | A task's status changes and its assignee didn't change in the same edit              | The assignee     |
| `task_commented`      | Someone comments on a task (`notifyTaskCommented`, called by the comment write path) | The assignee     |
| `mentioned`           | A saved document or task description newly `@`-mentions a person (`notifyMentioned`) | The person named |

Nobody is notified about their own actions, and tasks without an assignee notify no one. A notification about a task or document that has since been deleted is hidden, and so is a module notification whose subject has been deleted (see [The sweep](#the-sweep)).

## Module notifications: dates falling due and exceptions

The modules add two kinds of notification. **Due dates** are found by a periodic sweep; **exceptions** are created in the write transaction, like the task types. Each goes only to people who can read the module (`read` or more, `manage` where the table says so), and only while the module is active.

CCP checks do not notify one by one: they come round every few hours. Instead the sweep makes one **`ccp_checks_overdue` digest** per HACCP manager per day, naming (up to three, with a count) the scheduled CCP checks overdue by more than one of their own intervals (a check every 2 hours more than 2 hours late; a daily check more than a day past its due date). Per-batch checks and CCPs never checked are left out (the check sheet and the batch page show them). The key is the day, so the first sweep of the day that finds something creates it and later sweeps that day add nothing. Storage readings are not swept either, and an out-of-limit reading notifies as it is recorded. Complaints have no owner yet, so there is no "complaint assigned" type.

Module notifications carry `module` (the column), no actor for sweep types (`actorId` null), and `data`: `title` (what it is about, e.g. "Mixer: Strip and grease"), `subjectId`, `dueOn` and `dueState` (`soon`, `due`, `overdue`, `expiring`, `expired`, `missing`), and for training `staffId` and `staffName`. `notificationPath` (core) turns one into the page it links to (`/training/staff/<id>`, `/maintenance`, `/quality/nonconformances/<id>`, `/labels/<id>`, …), for the Inbox and the email; `describeNotification` (core) words it.

### Attendance

- **`missed_clock_out`** is swept (`sweepAttendance`, using `missedClockOuts` from the attendance service, which pairs events with the same `buildShifts` as the Shifts page). It is created once the clock-in is older than the workspace's maximum shift and only for clock-ins in the last `NOTIFY_LOOKBACK_DAYS`. The person's own copy links to the On site page (they can't open Shifts without `write`), the others to that day on Shifts. The attendance module has its own `notification_sweeps` row, so its first sweep is seeded without email like the others.
- **`visitor_arrived`** is an event notification with `module` null: the host usually has no attendance access and the Inbox would hide a module notification from them. The Inbox lists the type in their email preferences while attendance is on. It is deleted with the visit's retention period (`visitorRetentionMonths`) since it names the visitor.

Production's sweep (`sweepProduction`) also releases reservations whose last day has passed (reason `expired`, in the sync log) before it looks for reserved stock at risk.

### The sweep

`sweepDueNotifications` (`apps/server/src/services/notification-sweep.ts`) works out what has fallen due in every workspace and creates the notifications. It reuses each module's own "what's due" logic (`getDue` for HACCP, `getSiteDue`, `trainingDue`, the stale check of `listProductLabels`), so the Inbox agrees with the modules' pages.

- **Schedule.** The API runs it in-process every `NOTIFICATION_SWEEP_INTERVAL_SECONDS` (default 900; `0` turns it off), first about 10 seconds after start, and never overlapping itself. It is started in `index.ts` only, so tests never run it on a timer; they call it directly.
- **Quality programme.** The quality part of the sweep first plans the next audits of the recurring audit programmes (see the Quality module), so one planned close enough notifies its auditor in the same pass.
- **Callable.** Owners and admins can run it for their workspace now with `POST /v1/workspaces/:slug/notifications/sweep` (sessions only, `requireAdmin`), which returns `{ created }`.
- **Idempotent.** Every swept notification has a `dedupe_key` naming the subject and the due occurrence: `cleaning:<assetId>:<dueOn>`, `site:maintenance:<taskId>:<dueOn>`, `training:<staffId>:<courseId>:<dueOn or expiry>`, `audit:<id>:<plannedOn>`, `nc:<id>:<dueOn>`, `corrective_action:<module>:<id>`, `label:<id>`, `clock_out:<clock-in event id>`, `recipe_drift:<versionId>:<what changed>` (a further change of the declarations is a new drift and notifies again). A check never done uses `first` instead of a date, one due because the last record set no next date (a pest visit) uses `after:<last date>`, and hourly checks use the due moment. A unique index on `(workspace_id, user_id, dedupe_key)` with `on conflict do nothing` makes a second sweep create nothing. Once the record is done and falls due again, its due date, and so its key, changes, and it notifies again. A glass area is keyed on the latest due date among its due items (the Inbox shows the earliest), so checking only the oldest item while others are still overdue doesn't notify again.
- **Once per occurrence, no escalation.** The due state is not part of the key: training that notified as `expiring` does not notify again when it expires, and a check that notified as `due` does not notify again when it becomes `overdue`. The Inbox entry keeps the state it was created with; the module's "what's due" page shows the current one.
- **Recent occurrences only.** Occurrences that fell due more than `NOTIFY_LOOKBACK_DAYS` (14, `@knotworking/core`) before the sweep's day are skipped, as are corrective actions that passed `CORRECTIVE_ACTION_OPEN_DAYS` more than that long ago and audits planned before then. Without this, the first sweep after an upgrade, or the first sweep after someone gains `manage`, would send the whole backlog (and an email per item). Undated occurrences (a check never done, a pest visit with no next date) and stale labels are kept: there is at most one per subject. Older items stay on the modules' "what's due" pages.
- **Several API instances.** Each instance may run the sweep, but each workspace is swept in one transaction holding the workspace's advisory lock (`pg_try_advisory_xact_lock` on `knotworking:notification-sweep:<workspace id>`). Another instance arriving at the same moment skips that workspace instead of waiting, so only one instance does the work. Before inserting, the sweep drops drafts whose recipient already has the dedupe key, with one query per workspace (`dedupe_key = any(...)`), so a steady-state sweep writes nothing. The unique index still backs this up: each instance emails only the rows its own insert returned, so nobody gets a notification or an email twice.
- **Cheap where it can be.** Corrective actions are filtered by age in SQL (open, not deleted, and opened between `CORRECTIVE_ACTION_OPEN_DAYS` and that plus the look-back ago). Labels every current label manager has already been told about are left out in SQL before the stale check, which needs each label's recipe graph, so a steady-state sweep checks no labels.
- **The first sweep of a module is seeded without email.** `notification_sweeps` records, per workspace and module, that the module has been swept. When a module has never been swept in a workspace (the first sweep after the deploy that adds the sweep, a new workspace, or a module just switched on with `KNOTWORKING_MODULES`), its notifications are created in the Inbox but **not emailed**, so managers aren't emailed the whole backlog at once (on top of the look-back above, which limits what is created at all). From the next sweep on, new notifications are emailed as usual. The row is written in the same transaction as the notifications, and only for active modules. Event notifications (`reading_out_of_limit`, `nonconformance_assigned`) are never held back.
- **Deleted subjects.** The sweep skips deleted records (soft-deleted audits, assets, tasks, labels, courses, staff). A module notification whose subject has since been deleted is hidden from the Inbox and the unread count, like task and document notifications: audits, non-conformances (assigned or due), corrective actions (open or deviations recorded by hand), HACCP assets (cleaning and calibration), HACCP plans (hazard analysis review), maintenance tasks, labels, recipes (allergen drift), SOPs (review, approval and acknowledgement reminders), and for training the course or the person. Types whose subject is not one row (site checks, the pest control programme, readings, the CCP digest) are not hidden; archiving (a status) never hides a notification.
- **Clock.** A sweep decides everything at one moment (`now`, default the current time), passed down to each module's due logic, `getSiteDue` included.
- **Access at sweep time.** Inactive modules are skipped entirely. Recipients are worked out from each member's effective level (`memberAccess`, the same `resolveModuleAccess` as everywhere). The Inbox also hides a module's notifications from anyone who later loses read access, or while the module is switched off, and shows them again when access returns. Hidden notifications can't be marked read (by id or by "mark all read"), so they come back as they were.
- **Coalescing `readings_awaiting_review`.** A sheet of fifty readings from an agent must not send fifty emails. `notifyReadingsAwaitingReview` skips a manager who still has an unread entry of that type; once they read it, the next pending reading notifies again. Its `dedupe_key` is `review:<logId>`, `deviation_recorded` uses `deviation:<actionId>`, so retries never duplicate either. A deviation that answers an out-of-limit reading is announced once, as `reading_out_of_limit`.
- Event notifications (`reading_out_of_limit`, `readings_awaiting_review`, `deviation_recorded`, `nonconformance_assigned`) work out their recipients inside the write transaction and are emailed after it commits through `deliverNotifications`, which uses the mailer `createApp` registered for the database (`registerNotificationDelivery`), so module services need no callback parameter.

### Mentions

`mentioned` is created by `notifyMentioned` (`services/notifications.ts`), called inside the transaction of `createTask`, `updateTask` (only when the PATCH carries a `description`), `createDocument` and `updateDocument` (only when it carries `content`), with the stored body being replaced and the new one. Only mentions the save **adds** notify (`addedMentions` in `@knotworking/core`: distinct `user` mentions in the new body that the old body didn't have), so autosaving the same text, editing around an existing mention or renaming the page is silent. Removing a mention and typing it again later notifies again. Rules:

- Never the author, even for a self-mention.
- The mentioned user must be an active member of this workspace; ids of strangers, other workspaces and former members are ignored. Guests are members, and every guest can read every document and task of the workspace, so they are notified like anyone else.
- At most 50 people per save; a refused save (for example a `409 document_conflict`) creates nothing, because the notification insert is in the same transaction as the write.
- Preferences apply as for every type: the Inbox entry is always created, and the email (after commit, only with SMTP configured) goes to people who haven't turned email off. The email links to the page.
- Mentions in a **task description** set `taskId` and `data.taskTitle`, like the other task types. A document has no column in `notifications`, so mentions in a **document** store `data.documentId` and `data.documentTitle` (no schema change) and the Inbox links to `/<workspace>/docs/<id>`. Deleted documents hide their notifications like deleted tasks do (a join on `data->>'documentId'`).
- Like all notifications they are personal and never go through `recordChanges`. The document or task write itself still does.
- Comments are plain text today and have no mentions.

## Why notifications are not in the sync log

`notifications` is **per-user** data. The sync log (`sync_changes`) is per-workspace and every member reads all of it, so putting notifications there would broadcast each person's inbox to the whole workspace. Like `calendar_events`, notifications are therefore never passed to `recordChanges`. Clients fetch their own through the API instead:

| Route (under `/v1/workspaces/:slug`) | Purpose                                                                                                                             |
| ------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------- |
| `GET /notifications`                 | Newest first. `limit` (default 30, max 100), `before` (cursor), `unread=true`. Returns `{ notifications, nextCursor, unreadCount }` |
| `GET /notifications/unread-count`    | Just the count (used by the sidebar badge)                                                                                          |
| `POST /notifications/:id/read`       | Mark one read. Idempotent; 404 for someone else's notification                                                                      |
| `POST /notifications/read-all`       | Mark everything in this workspace read                                                                                              |
| `GET/PUT /notifications/preferences` | `{ emailEnabled, emailTypes }` plus `emailConfigured` (whether the server has SMTP)                                                 |
| `POST /notifications/sweep`          | Owners and admins (sessions only): run the due-date sweep for this workspace now. Returns `{ created }`                             |

Everything is scoped to the signed-in user. Guests can read and clear their own notifications. Paging uses the notification `id` as the cursor (UUIDv7, so id order is creation order). Clients that want fresh data poll `unread-count` or re-fetch the list; there is no push yet (see the sync protocol's SSE/WebSocket plan).

## How they are created

`createTask` and `updateTask` in `apps/server/src/services/tasks.ts` insert notifications **in the same transaction** as the task write (`notifyTaskCreated`, `notifyTaskUpdated` in `services/notifications.ts`), so a notification exists if and only if the change committed. The comment write path should call `notifyTaskCommented(tx, workspaceId, authorId, task, snippet)` inside its transaction the same way.

The sweep decides "due" on the workspace's calendar: today is today in the workspace's time zone (`workspaceTimeZone`, see [architecture.md](architecture.md#the-workspace-time-zone)), and each module's due logic it reuses works in the same zone, so a dedupe key such as `cleaning:<area>:<date>` names the local due date.

Notification rows store a snapshot of what they need to render (`data`: task title, new state name, comment snippet), so the Inbox needs no joins beyond the actor's name from the bootstrap snapshot.

## Email

When `SMTP_URL` is set, new notifications are also emailed through `apps/server/src/mailer.ts`, **after** the transaction commits and without delaying the response. Delivery failures are logged and never fail the write. Without SMTP nothing is sent (the Inbox still works).

Each member can opt out per workspace (`workspace_members.notify_email`, default on) with the switch at the bottom of the Inbox page, and turn email off for single types under "Choose which kinds are emailed" (`notification_preferences`, one row per type changed; no row means email on). The page lists only the types of modules the member can read. The Inbox entry is always created, whatever the preferences. `PUT /notifications/preferences` takes `{ emailEnabled?, emailTypes?: { <type>: boolean } }`; `GET` returns `emailTypes` for every type. Preferences are personal and never synced.

## Durable email delivery

Every new notification includes private pending-delivery fields in its transaction. The API starts a recovery worker independently of the due-date sweep; post-commit delivery remains the fast path. Workers claim individual notifications with expiring fenced leases, retry failed sends with backoff, and record sent/skipped state. Preferences, membership and module access are checked at delivery time. Existing inbox history is skipped when upgrading. SMTP remains at-least-once, so a crash between acceptance and recording success may duplicate an email.
