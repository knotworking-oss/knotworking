# Connect Xero and post financial documents

Knotworking sends approved supplier bills, issued customer invoices and issued customer credit notes to Xero. The optional Accounting module keeps the reviewed destination, financial lines and posting history in the [private accounting outbox](accounting.md#posting-lifecycle-and-isolation).

## Set up a test app and connect

1. In the [Xero Developer Portal](https://developer.xero.com/app/manage), create a **Web app** for acceptance. Choose a [Xero Demo Company](https://central.xero.com/s/article/Use-the-demo-company) with the intended base currency. Register this exact redirect URI, substituting your Knotworking web origin for `APP_URL`.

   ```text
   APP_URL/api/v1/accounting/xero/callback
   ```

   `APP_URL` must be the web origin alone (scheme, host and port, with no path) and must stay the same once bills are sent. Each bill links back to `APP_URL`, and recovering an interrupted posting searches Xero for that exact link. With a path, the API logs `Xero posting is off` at startup and every dispatch pass, and queued bills stay queued until it is fixed.

   Use HTTPS. Xero permits `http://localhost` for local testing, with the actual port. For example, register `http://localhost:3000/api/v1/accounting/xero/callback` for that local web origin. The callback goes through the web gateway, so it can read the initiating browser session. Configure any reverse-proxy access logs to omit the callback query string. See the [Xero authorisation code flow](https://developer.xero.com/documentation/guides/oauth2/auth-flow/).

2. Set `XERO_CLIENT_ID`, `XERO_CLIENT_SECRET` and a private `BETTER_AUTH_SECRET` of at least 32 characters in the API environment. With Compose, use `deploy/.env`. Give all API workers the same values. Enable `accounting` and the workspace's required modules in `KNOTWORKING_MODULES`. Keep Items and Purchasing available to the people who review suppliers and bills. Enable Stock for stocked purchases. Apply the migrations and restart the API. Set `ACCOUNTING_DISPATCH_INTERVAL_SECONDS=0` during acceptance if you want to control the exact send using **Send now**.
3. In Knotworking, a signed-in workspace owner or admin with Accounting manage access opens **Accounting connections**, saves a Xero setup and selects **Connect Xero**. Sign in and authorise the Demo Company. The app requests `offline_access`, `accounting.invoices`, `accounting.settings.read` and `accounting.contacts.read`. See [Xero scopes](https://developer.xero.com/documentation/guides/oauth2/scopes/).
4. Return to the original browser session. Under **Authorised organisation**, select the Demo Company and choose **Review organisation**. Compare the displayed name, tenant ID and base currency with your intended ledger, then choose **Confirm organisation and currency**. The currency must match the workspace currency and use two decimal places. The workspace defaults to GBP, and changing its currency does not convert any values. Use **Verify connection** to check the saved organisation and currency.

The consent flow expires after ten minutes and the callback state is single-use. Expired sign-in attempts, with any unconfirmed credentials they hold, are deleted every ten minutes. One Xero sign-in can authorise several organisations. After you confirm one, Knotworking removes the others authorised in that sign-in from its Xero connections, unless another setup uses them. This is best-effort and logged; check Xero's **Connected apps** if an organisation you didn't choose still lists Knotworking. Tokens stay server-side and are encrypted with AES-256-GCM using a key derived from the private server secret and Xero client ID. Access tokens are refreshed five minutes before they expire. Workers lock the credential row when exchanging a refresh token and persist the rotated pair together. Confirm and disconnect call Xero before taking the workspace's ledger lock, then check the attempt, setup revision and credentials again before saving. If you change the server secret or Xero client ID, reconnect affected setups.

## Review mappings and send a bill

1. Open the connection's **Reviewed mappings**. In the selected Xero organisation, identify the existing supplier contact, active account codes and applicable tax types. Save a supplier mapping to the Xero `ContactID` (UUID), account mappings to Xero account codes, and tax mappings to Xero `TaxType` codes. Record what you reviewed in each mapping reason. Use the Xero API's [Contacts](https://developer.xero.com/documentation/api/accounting/contacts/), [Accounts](https://developer.xero.com/documentation/api/accounting/accounts/) and [TaxRates](https://developer.xero.com/documentation/api/accounting/taxrates/) resources to confirm the values.
2. Create and send a purchase order, record its receipt, create a matched purchase invoice with the supplier's invoice number, invoice date, due date and VAT, and approve it. A non-stock service can be received and matched without Stock. Under the connection, choose **Prepare approved invoices**, pick the invoice, check the destination and code every line. Confirm the line net and tax amounts printed on the invoice. For a Xero connection, preparation is blocked until the invoice has a due date on or after its invoice date and the supplier is mapped to a Xero `ContactID`. Approved invoices can't be edited, so correct a missing due date with a revised version.
3. In **Accounting queue → Queued**, use **Send now**, or let the dispatcher send it. A prepared invoice keeps its original tenant and reviewed mappings. The adapter checks the confirmed organisation, currency, lock dates, due date, supplier contact, account codes and tax types before writing. Each line's tax must match the tax type's Xero `EffectiveRate` applied to its net amount, within 1p, and a 0% rate allows no tax. If Xero doesn't return a rate, Xero's own validation still applies. A failed check rejects the bill with its reason and writes nothing. It writes one `ACCPAY` bill with `AUTHORISED` status and exclusive amounts. Each reviewed financial line becomes a quantity-one line with the reviewed net and tax. Xero records the supplier's bill number and a URL to the source purchase invoice.

   Xero allows 60 calls a minute per organisation. The organisation, chart of accounts, tax rates and contacts are read once per dispatch pass and reused for a minute. If Xero rate-limits a call (`429`), before or on the create call, nothing was written: the bill goes back to **Queued** and that organisation's other bills wait for the next pass, which sends with the same `Idempotency-Key`.

4. In **Posted**, open the result and record the Xero invoice ID. In Xero, compare the supplier, invoice number, dates, account and tax codes, net, tax and gross against the source, and follow the source link. Knotworking confirms the posting after reading the Xero bill back and comparing those fields. See the [Xero invoice contract](https://developer.xero.com/documentation/api/accounting/invoices/).

## Send a customer invoice or credit note

1. Enable Customers and Invoicing in the workspace. In **Reviewed mappings**, select the existing customer and save its Xero `ContactID`. Review active revenue account codes and output tax types. Invoicing retains its own issued numbers, dates and line totals.
2. Issue the invoice locally. In **Prepare customer invoices and credit notes**, select it and code each line with reviewed revenue and tax mappings. Send it from the Accounting queue. Xero receives an authorised `ACCREC` invoice with the issued number, dates, source URL and tax-exclusive financial lines. For customer documents, each Xero account must be active and of class `REVENUE`, and the applicable tax type must have a known `EffectiveRate` (or be `NONE`). Read-back checks identity, status, dates, contact, currency, exact totals and the line descriptions, account codes and tax.
3. Issue a local credit against eligible lines of the original invoice. Verify that the original invoice posted to this same Xero connection. Review the inherited contact, line coding and original Xero invoice ID, then choose whether to allocate the full credit. Leave the allocation box clear to post a credit on account, for example when the original invoice is already paid. If Xero rejects a prepared invoice or credit, for example because the original was paid before an allocated credit was sent, prepare it again with the corrected coding or without allocation. Knotworking replaces the rejected snapshot and keeps it in the posting history.
4. Xero receives an authorised `ACCRECCREDIT` at `PUT /CreditNotes`, with the local `CreditNoteNumber` and a `Reference` containing the posting UUID and original invoice number. The credit contract has no source URL field. If allocation is selected, the adapter checks the original invoice's outstanding balance and makes a separate `PUT /CreditNotes/{CreditNoteID}/Allocations` with the original Xero invoice ID, exact amount, date and a distinct stable idempotency key. It verifies the issued credit and requested allocation by reading `GET /CreditNotes/{CreditNoteID}`. The credit and its allocation are verified separately. Once the credit is verified it is **Posted**, even if the allocation then fails (for example, the invoice was paid between the balance check and the allocation, a rate limit, or a lost response). The queue shows the allocation as pending. Choose **Allocate to original invoice** to read the credit back and allocate it only if the allocation is not already there; a new allocation uses a new idempotency key. If the invoice was paid or settled another way, finish the credit in Xero and choose **Record as settled** with a note. The queue contains the verified Xero ID and links to the Knotworking credit. See the [Xero Accounting OpenAPI contract](https://github.com/XeroAPI/Xero-OpenAPI/blob/master/xero_accounting.yaml).

For **Needs checking**, customer invoices use the contact, date and source URL. Credit notes use the credit number to find a candidate and read it by ID to verify the `Reference`, original invoice, amounts and any requested allocation. Read-back confirms a credit without its allocation; an allocation that was requested is then pending and is settled from the posted credit as above. The recovery action reads only. An ambiguous result or rate limit after a successful write remains **Needs checking**.

## Reconnect, disconnect and recover an interrupted posting

- **Reconnect required.** If Xero refuses an access token (`401`), Knotworking marks it expired, refreshes it once and repeats the call. Only a refresh Xero refuses (`invalid_grant`, such as revoked consent or an expired refresh grant) needs a reconnect. If Xero refuses the organisation (`403`), Knotworking checks Xero's connection list; when the organisation was disconnected from Knotworking in Xero, the setup shows **Reconnect required** and its bills stay queued until you reconnect. Any other `403`, such as a connected user without permission, rejects the bill without a write. In each case, choose **Reconnect Xero** and confirm the original organisation. Use **Verify connection** before resuming work. Existing postings still refer to the original destination. A different organisation needs a different setup.
- **Pause or disconnect.** Disable a setup to pause preparation and sending while retaining access for read-back. **Disconnect Xero** tries to remove that tenant connection in Xero, then removes the local credentials. If Xero could not confirm the removal, finish it in Xero's **Connected apps**. Existing posting history stays available. Reconnect the same organisation to resume.
- **Needs checking.** Open the original posting and enter a review note. Choose **Find and verify in Xero** to look up the original bill by its reviewed contact, invoice date and unique source link. You can also find the bill manually and enter the Xero invoice UUID to check directly. Search results must identify one matching bill and pass full read-back. If the result stays uncertain, review it in Xero before taking further action. An uncertain attempt is never resent by Knotworking.
- **Rejected.** Check the history for the reason. A retry uses the original snapshot, including its mappings and line values. Retry after fixing an external condition such as an inactive account or lost consent. Making a new mapping in settings does not change a prepared bill. Every attempt sends the posting UUID as Xero's `Idempotency-Key`. Xero keeps a key for six minutes and replays its stored response, so a retry within six minutes of a validation rejection returns the same refusal. Neither response creates a bill. Wait six minutes and retry.

## Access and automated verification

Connect, review, confirm, verify and disconnect are available only to a signed-in workspace owner or admin with Accounting manage access. Personal API tokens and MCP are refused, and the callback runs the same membership, admin and module checks before it uses the state. The OAuth state is single-use and tied to the initiating sign-in session, workspace and connection.

The fake-Xero suites need no Xero account:

```sh
pnpm --filter @knotworking/server exec vitest run --maxWorkers=2 src/accounting-xero.test.ts src/accounting/adapters/xero.test.ts
```

They cover session-bound consent, refresh and revoked consent, a refused access token refreshed once, rate limits before and on the create call, an organisation disconnected in Xero, removal of unchosen organisations, expired sign-in sweeps, lock dates, tax-rate checks, stock and non-stock bills from purchase order to Xero, an interrupted create response, two bills with the same source link, double dispatch, disabled and disconnected setups, a wrong organisation and definitive rejection. PGlite runs one transaction at a time, so concurrent refresh across API processes has a separate test that needs a disposable Postgres database:

```sh
TEST_POSTGRES_URL=postgres://… pnpm --filter @knotworking/server exec vitest run --maxWorkers=2 src/accounting-xero.postgres.test.ts
```

The same fake transport covers partial shipments, signed-off billable hours, sales and credit read-back, credit allocation, duplicate preparation, rejected tax rates, deferred and interrupted sends, and local PDF output with the Xero connection disabled.

### Open questions

- Confirm the pilot workspace and Xero organisation use the same base currency. The implementation uses the configured workspace currency, with GBP as the existing default.
- Confirm the Xero app's scopes before acceptance. Knotworking requests the granular `accounting.invoices` scope, which apps created on or after 2 March 2026 must use, rather than the broad `accounting.transactions`. Check the app's settings against [Xero scopes](https://developer.xero.com/documentation/guides/oauth2/scopes/). If they differ, change `xeroScopes` in `apps/server/src/accounting/xero-http.ts`.
- Confirm who approves supplier invoices and who reviews the accounting coding. This increment uses the existing single-approver Purchasing flow. The approver and the accounting reviewer may be the same person if their role grants both permissions.

- Confirm customer invoice and credit number prefixes against existing Xero numbering. Local defaults are `INV-` and `CN-`, each followed by a six-digit workspace sequence.
