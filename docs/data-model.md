# Data model

Defined in [`packages/db/src/schema.ts`](../packages/db/src/schema.ts) (the platform: identity, auth, teams, attachments, notifications, API tokens, the sync log) and one file per module in [`packages/db/src/schema/`](../packages/db/src/schema) (`tasks.ts`, `docs.ts`, `time.ts`, `calendar.ts`, `assets.ts`, `items.ts`, …), all re-exported from `schema.ts`. Migrations live in `packages/db/migrations` and are generated with `pnpm db:generate`.

The Phase 3.1.2 forward distribution impact is a read model over production records (net of reversals), stock lots/movements and confirmed despatch lines. It uses a single read-only repeatable-read transaction and introduces no tables or migrations. Bounded breadth-first traversal deduplicates batch/lot paths; recipient rows are unique by despatch line, with distinct customer/despatch counts. Historical despatch snapshots provide contact details; access requires both Despatch and Production.

## Entities

Phase 3.1 adds `customers`, `despatches` and `despatch_lines` (schema files `customers.ts` and `despatch.ts`; migration `0056_customer_despatch`). Customers are shared reference data independent of future sales/pricing access. Despatch headers reference a customer and preserve business/contact and delivery-address snapshots on confirmation. Lines reference an item, lot, location and the original/reversing stock movements, with quantities in base units and a frozen display unit/code/name/expiry. Confirmed rows are immutable except for a one-time void stamp and reversal pointers; only draft lines can be replaced. All records carry `workspace_id`; every lookup is scoped. Customer/despatch sync is metadata only, with no contacts or addresses. These modules use paginated queries rather than bootstrap collections. Their stock movements extend the existing ledger with `despatch`, included net of reversals in mass balance and recall-test reconciliation. See [the module contract](modules.md#customers-and-despatch-phase-31).

```
workspace ─┬─ workspace_members ── users
           ├─ teams ─┬─ team_members
           │         ├─ workflow_states   (per-team, each in a category)
           │         └─ tasks ─┬─ task_labels ── labels
           │                    ├─ comments
           │                    ├─ task_relations (blocks / blocked by)
           │                    ├─ time_entries ── users
           │                    ├─ attachments (also on documents and module records)
           │                    └─ tasks (parent/subtasks)
           ├─ projects ── project_teams ── teams
           ├─ documents (tree via parent_id; optional team/project) ── document_revisions
           └─ sync_changes (append-only change log)
```

## Conventions

These are what make the schema work for offline, multi-device clients:

| Convention                                                        | Why                                                                                                                                                            |
| ----------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **UUIDv7 primary keys**, which clients may generate               | Records can be created offline without collisions. IDs are time-ordered, which is good for B-tree locality.                                                    |
| **`workspace_id` on every row**                                   | One filter for sync, authorization and future row-level security or sharding.                                                                                  |
| **`created_at` / `updated_at` / `deleted_at`**                    | Soft deletes propagate to offline clients as tombstones. Join rows such as `task_labels` are hard-deleted, and the delete is still recorded in the change log. |
| **Text columns for enums**, validated in `@knotworking/core`      | New values ship without blocking migrations. Older clients can tolerate unknown values.                                                                        |
| **Fractional-index `sort_order` strings**                         | Reordering touches one row, and concurrent reorders merge cleanly. Compare with byte order, not locale collation.                                              |
| **Rich text as JSON block trees** (ProseMirror/Tiptap-compatible) | Portable to every client and ready for collaborative editing. `docToPlainText` gives search and preview text.                                                  |
| **Heavy fields loaded lazily**                                    | Bootstrap excludes task descriptions and document content. They are fetched per entity.                                                                        |

## Changing the schema

1. Edit the module's file in `packages/db/src/schema/` (or `schema.ts` for platform tables; `relations.ts` if needed).
2. `pnpm db:generate` writes a new SQL migration. Review it.
3. `pnpm db:migrate` applies it locally.
4. If the change affects what clients see, update the schemas in `@knotworking/core` and, for new entity types, `syncEntityTypes`.

Prefer additive, backwards-compatible changes. Desktop and mobile clients may run older versions for a while.

Phase 3.1.3 adds `quality_incidents` (case/owner/assessment/signed closure), `quality_incident_snapshots` (immutable complete recipient rows with explicit trace coverage), `quality_incident_holds` (unique case/lot, independent of QA status), and `quality_incident_events` (append-only evidence, containment/release audit and corrections). These are tenant-scoped with no delete workflow. Contacts/narratives are excluded from sync; command receipts make repeats safe. Corrections invalidate prior evidence without editing it. Releasing an incident hold leaves QA quarantine in place.

Phase 3.1.4 adds `customer_delivery_sites` (per-account case-insensitive code, delivery contact/address, active/archive), allocation/packing/load sign-off fields and historical site fields on `despatches`, `despatch_handling_units` (lifetime-unique optional SSCC and immutable contents, superseded rather than deleted), `despatch_operation_events` (signed evidence and original allocated/packed line snapshots), `despatch_proofs` (cumulative delivery quantities and explicit predecessor correction), and `despatch_returns` (original delivery line/lot, new quarantine lot, physical receipt movement, disposition evidence and optional case link). Returns use the new `customer_return` movement type; correcting a receipt appends its opposite and marks the receipt void. Original shipments remain unchanged. No new bootstrap collections or sync entity types are required. Allocations use existing draft line quantities and an active allocated header, so confirmation/void/release ends the hold atomically.

Phase 3.3.1 adds `authenticity_assessments` (item/supplier scope, active/archive, current/draft pointers and monotonically increasing update stamp), `authenticity_versions` (ordered draft/signed/superseded JSON assessments with subject snapshots and sign-off), `authenticity_triggers` (append-only source-backed signals resolved by a signed version), and `authenticity_verifications` (version/control-bound dated evidence with retained manager corrections). Partial unique indexes allow at most one active scope per item/supplier (including all-sources null), one draft and one signed version per assessment. Only draft content is editable; previous signed content/signatures remain unchanged. Approved version bodies carry stable control ids; verification is version-specific, so history does not implicitly verify a replacement plan. References to test samples are validated at write time rather than copying laboratory data. No bootstrap collection is added; `quality_authenticity` sync rows contain only id/reference/status/update metadata.

## General business workflows

- Project templates create ordinary project, team and task rows. The command receipt ties a retry to its original project ID.
- `purchase_requests` stores the requester and designated approver, the submitted amount and currency, and the final decision with actor, timestamp and note. Records are private to participants and module managers.
- `service_quotes` stores the customer snapshot, fee or hourly rate, quoted minutes if applicable, and the linked delivery project. Delivery sign-off records approved minutes for hourly work. `service_quote_events` retains signed revisions and reasons. Only quote IDs and revisions enter the sync log.

## Sales (3.4.1)

- `sales_orders`: shared customer/site IDs, quote/order kind, status, revision, retained recipient/address facts, currency, customer reference, terms, notes, optional source quote, creation and latest signed decision. A source quote creates at most one draft order. Customer changes never rewrite signed history.
- `sales_order_lines`: stable line UUIDs, position, item/code/name snapshot, entered and base quantity/units, daily due date, eight-place unit price, optional source price agreement, note and removal timestamp. Removed draft/unlinked lines are retained; full preceding versions are in events.
- `sales_prices`: dated customer/item/currency price agreements, price unit, contract reference and terms, actor and archive evidence. Inclusive overlap checks run under the workspace lock. Prices are numeric(18,8); quantities are numeric(18,4).
- `sales_events`: append-only document snapshots, unique document revision, action, reason and actor. The original document, every signed amendment and link-correction decision remain queryable with paginated history.
- `sales_fulfilments`: whole despatch-line assignments to sales order/line IDs. One live assignment per despatch line; signed corrections retain the prior link. Confirmed despatch and non-voided return records supply shipped/returned quantities; Sales itself posts no stock.
- `sales_external_references`: immutable workspace/system/type mapping between durable local UUIDs and external identifiers, unique in both directions. No provider credentials or connection is stored here.

Every table is workspace scoped. Ledger command receipts make writes retry-safe; reviewed document revisions and the workspace lock serialize competing amendments/fulfilments. Sales sync contains ID/revision invalidation metadata only. Commercial document contents, price agreements and history are paginated reads behind Sales permission; distribution details additionally require Despatch read. Daily confirmed commitments are separate from weekly forecasts, with no automatic Demand writes or forecast addition. See the Sales contract in `modules.md` for ownership and external-adapter limits.

## Health, safety and environment (3.4.3)

- `hse_records`: workspace-scoped stable title/kind, revision, active/archive state and creation metadata. `hse_versions` retains draft, approved, superseded and archive-decision content, reviewer/time/reason; unique current-draft/current-approved indexes preserve the controlled-document lifecycle. Content stores the risk/COSHH/contractor/inspection/environmental scope, review/check schedule, evidence and references to existing Tasks/Items/Training records.
- `hse_entries`: append-only checks, exercises, waste transfers and resource use against the signed version, business/period dates, result, actions, evidence, next due date and positive numeric(18,4) quantity with the signed unit. Explicit failure resolutions and signed correction stamps retain preceding evidence. No HSE quantity posts stock.
- `hse_permits`: reviewed work body, an existing asset of the register (`assets`), isolation flag, revision/state and issue/resume evidence snapshot. `hse_permit_events` retains every draft edit and signed issue/suspend/resume/close/cancel decision, including return-to-service assertions and actor. Open issued/suspended isolation permits block Site hygiene clearance independently of module visibility; expiry alone never releases one.
- `hse_incidents` and `hse_incident_events`: separately permissioned, person-only accident/near-miss/environmental investigations and immutable private audit snapshots, with affected existing staff, health evidence, reporting decisions and signed closure. No rows or invalidation metadata enter workspace sync; there is no generic private attachment target.
- `hse_incident_injuries` and `hse_incident_actions`: the people hurt on a restricted incident (name, People record, person type, injury, body part, treatment, days absent; soft-deleted when replaced; read only by signed-in incident managers), and owned corrective actions (owner, due date, open/done/cancelled, completion note). Never synced.

Normal HSE sync entities (`hse_record`, `hse_entry`, `hse_permit`) contain IDs/revisions only. Full registers, versions, entries, permits and private histories are queried through paginated guarded endpoints. Attachment targets reuse the existing storage and HSE access checks with append-only file retention. Workspace business dates, durable command receipts and the workspace lock apply to all decisions. The Training port reuses its existing competence/SOP rules and returns the exact source training record/sign-off references; HSE creates no shadow staff, supplier, training or maintenance register.

## Accounting setup and private integration records

`accounting_connections` stores optional provider/company metadata, display name, revision and disable state. Its composite workspace/id key preserves connection UUID namespaces across tenants. Company is empty until supplied, then immutable. The provider/company lookup prevents accidental duplicate setup through the service. Imported foundation destinations have no invented creator.

`accounting_mappings` links a connection's supplier/customer UUID or account/tax semantic key to an opaque external reference. The composite connection foreign key enforces tenant ownership. Mappings can be withdrawn; reviews increment the connection revision and append `accounting_configuration_events` containing actor, reason and prior/current values. All writes are transactional under the workspace lock with command receipts. These tables and the existing `accounting_postings`/`accounting_posting_events` are private integration data, deliberately excluded from shared workspace sync. Connection disable state is rechecked when enqueueing and claiming; reconciliation of previous uncertain work remains possible.

## Private workforce absence records

`workforce_absences` references existing People staff and holds kind, state, inclusive start/end dates (null end only for ongoing sickness), submission/HR notes, author, self-service requester and revision. `workforce_absence_events` retains each revision's state/dates/notes plus actor, reason and time. HR records and events are private and intentionally excluded from shared workspace sync. Self-service selects an explicit non-HR projection and requires both the current staff link and original requester; People relinking cannot disclose an earlier submitter's private record.

Creation, decisions, correction and withdrawal use the workspace lock and durable command receipts. People deletion takes that lock and refuses staff with absence history; a staff number with that history is also fixed. The public planning projection unions overlapping approved/reported/recorded date ranges and exposes no kind, narrative, review state or private record id. Current employment/competence/clocking remain separate authoritative sources; this is not a staffing/attendance/payroll ledger. Details and bounds are in [Workforce delivery](workforce.md).

## Rotas, agency engagements and staffing requirements

`workforce_shifts` (name, start/end time, optional production line, active), `workforce_working_patterns` (person, shift, weekday mask, optional role, valid dates), `workforce_rota_entries` (person, shift, start date, optional role and pattern, note, active/cancelled with who and why; at most one active entry per person, shift and date), `workforce_agencies` and `workforce_agency_engagements` (an agency supplying a People record between dates, with its reference) and `workforce_staffing_requirements` (shift, headcount, optional job role, Training course IDs, weekday mask, `always` or `production_planned`, valid dates, active). Every row has a revision; changes use the workspace lock and durable command receipts. They are private planning records outside shared sync. Rota entries and engagements reference staff, so they keep history if a person later leaves or is deleted.

## Payroll runs

`workforce_payroll_runs` holds one pay period's snapshot (`PayrollRunSnapshot` in core: employees with hours and absence days, agency workers apart, copied package references, warnings), its SHA-256, version and `supersedes_id`, state (`prepared`, `approved`, `superseded`), preparer, approver, note and revision. `workforce_payroll_run_events` is the append-only history (prepared, approved, exported with adapter and file hash, correction prepared, superseded). Both are private and outside shared sync; exported files aren't stored.

Standards gap analysis (G1, governance module): `governance_standards` (code, name, issue, publisher, status; code and issue unique), `governance_standard_clauses` (clause reference unique per standard, title, text from the workspace's own licensed copy, section and section title, fundamental), append-only `governance_clause_assessments` (status, note, owner, due date, who and when; the latest is the clause's state) and `governance_clause_tasks` (tasks raised to close findings). G2 adds `governance_clause_evidence` (which automatic evidence checks support a clause; one live row per clause and check, soft-deleted when unmapped). Check results are computed on read, never stored. G3 adds `governance_clause_drafts` (proposed findings, usually an agent's: status, finding, basis, suggested owner and date, drafted via agent or person, state open/accepted/dismissed/superseded with who decided and the resulting assessment; one open per clause) and `governance_gap_snapshots` (a frozen copy of a standard's gap analysis: name, workspace date, taker, clause count and a JSON payload of every clause with its evidence results; never edited, only the header synced).

## Business intelligence

`workspaces.financial_year_start_month` (1–12, default 1) sets the financial year dashboards and reports use for "this financial year", quarters and year to date; it is part of the workspace settings and the bootstrap, and changes sync as a `workspace` change.

Dashboard tables (`packages/db/src/schema/bi.ts`): `bi_dashboards` (scope `workspace` or `module:<id>`, title, description, spec, status `draft`/`published`, audience `workspace`/`members` with `audience_user_ids`, version, owner, published and archived by whom, `is_template` for dashboards offered under "New dashboard"), `bi_dashboard_versions` (one row per saved version, append-only), `bi_snapshots` (frozen board snapshots with the view they were taken with, append-only; `kind` is `dashboard` or `analysis`, a verified agent analysis whose figures, sources and formulas are in `results.analysis`) and `bi_board_packs` (ordered snapshots with commentary and a cover; `draft` until issued to an audience, then never changed). Sync-log handling: `bi_dashboards` and `bi_dashboard_versions` (definitions and their history) are written in a transaction that calls `recordChanges`, and `redactChanges` filters them by audience: a dashboard the member may not open arrives as a tombstone, and version history goes only to those who may edit it. Snapshots and packs record header-only changes (`bi_snapshot` to people who manage dashboards, `bi_board_pack` to its readers): no spec, results, cover or commentary. Query results and snapshot figures are never in the sync log: results are computed per viewer through the API, and snapshot figures are read through the API. Snapshots themselves are append-only.

Analytic queries never write: they run read-only under the analytic guard (`apps/server/src/services/bi/guard.ts`) with a planner cost ceiling, a Postgres `statement_timeout`, a row cap and a process-wide concurrency limit.
