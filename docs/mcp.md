# MCP server (AI agents)

`apps/mcp` (`@knotworking/mcp`) is a [Model Context Protocol](https://modelcontextprotocol.io) server. It lets an AI agent (Claude Code, Claude Desktop, or any MCP client) read and write Knotworking: tasks, projects, documents and comments.

It is just another API client. It uses `@knotworking/api-client` and the helpers in `@knotworking/core`, never the database, so the agent can do exactly what its API token allows through the normal API, and nothing else.

Phase 3.1 adds customer tools (`list_customers`, `create_customer`, `update_customer`, module `customers`) and distribution tools (`list_despatches`, `get_despatch`, `draft_despatch`, `get_lot_recipients`, module `despatch`). They use shared core request schemas and explicit customer/lot/location UUIDs. Customer and despatch lists are paginated. Drafting creates no stock movement; confirmation of physical despatch and voiding a ledger record are a signed-in manager's acts and are never offered to tokens. `get_lot_recipients` reports direct deliveries of the selected lot only, not ingredient-to-output recall impact. Contact details are protected by the modules' grants. See Phase 3 for the next increments.

```
agent ──MCP──▶ mcp (:4100, /mcp) ──Bearer knw_…──▶ api (Hono) ──▶ Postgres
               stateless, stores nothing           the usual permission checks
```

Two transports share one tool set:

| Transport                       | Use it for                                           | Entry                  | Credentials                                                                           |
| ------------------------------- | ---------------------------------------------------- | ---------------------- | ------------------------------------------------------------------------------------- |
| **Streamable HTTP** (stateless) | A shared server: your team's compose stack, or local | `dist/http.js`, `/mcp` | The caller's `Authorization: Bearer knw_…` header, forwarded to the API on every call |
| **stdio**                       | A client that launches the server as a local process | `dist/stdio.js`        | `KNOTWORKING_API_TOKEN` in the process environment                                    |

In HTTP mode the server keeps no token and no session: every request builds a fresh MCP server, calls the API with that request's token, and forgets it. A request without a token gets `401` with `WWW-Authenticate: Bearer`.

Phase 3.1.2 adds `get_distribution_impact` (Despatch plus readable Production). Arguments: `lot_id` UUID, `depth` (1–20, default 10), `limit` (up to 200, default 50) and `offset` for delivery lines. It returns affected lots, production batches, original recipient snapshots, distinct counts and explicit recorded-data coverage. Respect partial reasons and resource limits even when there are no known deliveries; do not present it as a completed recall or add quantities in unlike units. The MCP catalogue's `requiresModules` gate hides this cross-module report when either module is unavailable; the API independently enforces both on every request.

## The in-app assistant and your own agent platform

Knotworking also has a chat sidebar (⌘J, [assistant.md](assistant.md)) that runs a model through a member's own API key and reaches the workspace through this same MCP server, with a temporary 15-minute token of theirs. That token is minted by the API for one turn, never appears in the token list and is revoked when the turn ends. Set `MCP_INTERNAL_URL` to the address the API uses to reach this server (compose does it for you).

If you already use an agent platform (Claude, ChatGPT, Claude Code, Codex, or any MCP client), you do not need the sidebar: create a personal token below and connect that platform to `/mcp`. Both routes act with the same permissions.

## 1. Create an API token

Tokens belong to a person and act with that person's permissions.

**In the app:** open the user menu (bottom of the sidebar) and choose **API tokens** (`/<workspace>/settings/api-tokens`). Give the token a name, choose **Read only** (the default) or **Read and write**, untick any **modules** the agent doesn't need, pick an expiry (30, 90, 180 or 365 days; 90 by default) and create it. The token is shown **once**, in a panel that stays until you dismiss it, together with ready-to-copy setup snippets built from the address you are using: the `claude mcp add` command for Claude Code and a stdio JSON entry for Claude Desktop. The same page lists your tokens (name, scope, `knw_xxxx…` prefix, created, last used, expiry) and revokes them after a confirmation. You can hold at most 25 active tokens.

**From a script:** the same thing through the API with a signed-in session (a token cannot create tokens, which is why you sign in first):

```bash
BASE=http://localhost:3000          # your APP_URL (the web app proxies /api/* to the API)

# Sign in. Cookie-authenticated writes must send an Origin that matches APP_URL.
curl -s -c jar.txt -X POST "$BASE/api/auth/sign-in/email" \
  -H "Content-Type: application/json" -H "Origin: $BASE" \
  -d '{"email":"ada@knotworking.dev","password":"knotworking-demo"}'    # the demo login

# Create a token. scope is "read" or "write"; expiresInDays is optional (1-365).
curl -s -b jar.txt -X POST "$BASE/api/v1/me/api-tokens" \
  -H "Content-Type: application/json" -H "Origin: $BASE" \
  -d '{"name":"Claude Code","scope":"write","expiresInDays":90}'
# → {"token":"knw_…","apiToken":{"id":"…","scope":"write","prefix":"knw_ku9d",…}}
```

The `token` value is shown **once**; only its hash is stored. Keep it like a password (the web page keeps it in memory only: never in a URL, in local storage or in server-rendered HTML). `GET /api/v1/me/api-tokens` lists your tokens (prefix, scope, last used) and `DELETE /api/v1/me/api-tokens/:id` revokes one. In development you can also call the API directly: `http://127.0.0.1:4000/api/auth/sign-in/email` and `http://127.0.0.1:4000/v1/me/api-tokens`.

Start with a **`read`** token if you only want an agent to look things up. A `read` token can only make `GET`, `HEAD` and `OPTIONS` requests, so every write tool answers `token_read_only`.

Tokens expire after **90 days** unless you pass `expiresInDays` (1–365). Rotate them before then; there is no never-expires option.

## 2. Run it

### Development

```bash
pnpm dev                                   # starts the API, the web app and the MCP server (:4100)
pnpm --filter @knotworking/mcp dev         # or only the MCP server (needs the API on :4000)
```

It listens on `http://127.0.0.1:4100/mcp` (health check: `/health`). Check it with curl:

```bash
curl -s http://localhost:4100/mcp \
  -H "Authorization: Bearer knw_…" \
  -H "Content-Type: application/json" -H "Accept: application/json, text/event-stream" \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}'
```

### Docker Compose (self-hosting)

`compose.yaml` runs an `mcp` service next to the API (Docker target `mcp`, built with the other images) and `deploy/Caddyfile` serves it at **`<APP_URL>/mcp`**, on the same address and certificate as the web app. Nothing else needs configuring:

```bash
docker compose --env-file deploy/.env up -d --build
# agents connect to https://knotworking.example.com/mcp  (or http://192.168.1.20:3000/mcp on a LAN)
```

The container is not published on its own. To keep MCP off the network entirely, delete the `@mcp` block in `deploy/Caddyfile` (or remove the `mcp` service). If you run your own reverse proxy, forward `/mcp` to `mcp:4100`, keep the `Host` header, and don't buffer or rewrite the body. See [self-hosting.md](self-hosting.md).

### stdio

```bash
pnpm --filter @knotworking/mcp build
KNOTWORKING_API_URL=http://127.0.0.1:4000 KNOTWORKING_API_TOKEN=knw_… node apps/mcp/dist/stdio.js
```

For a self-hosted server, the API itself isn't reachable from outside, but the web app proxies it: use `KNOTWORKING_API_URL=https://knotworking.example.com/api`. Logs go to stderr because stdout carries the protocol.

## 3. Connect a client

**Claude Code**, against a running HTTP server:

```bash
claude mcp add --transport http knotworking http://localhost:4100/mcp \
  --header "Authorization: Bearer knw_…"
# self-hosted: https://knotworking.example.com/mcp
```

**Claude Desktop** (and any client that launches a local command), in `claude_desktop_config.json`:

```json
{
  "mcpServers": {
    "knotworking": {
      "command": "node",
      "args": ["/absolute/path/to/knotworking/apps/mcp/dist/stdio.js"],
      "env": {
        "KNOTWORKING_API_URL": "http://127.0.0.1:4000",
        "KNOTWORKING_API_TOKEN": "knw_…",
        "KNOTWORKING_DEFAULT_WORKSPACE": "acme"
      }
    }
  }
}
```

Run `pnpm --filter @knotworking/mcp build` first so `dist/stdio.js` exists. Other clients that support remote MCP servers with custom headers can use the HTTP URL and the `Authorization` header the same way as Claude Code.

### Choosing tools

The tool list is sent to the agent at the start of every conversation and stays in its context. Listing every tool natively is large: with every module on it is 286 tools, about 97,000 tokens. So by default the server lists a small core and lets the agent pull in the rest on demand (**catalogue mode**).

#### Catalogue mode (the default)

A connection lists about 15 tools (about 4,000 tokens with every module and action on):

| Tool                                                                                                                                               | What it is for                                                                                                                                                                                                                                                                                          |
| -------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `list_workspaces`, `get_workspace_overview`                                                                                                        | Orientation. In catalogue mode the overview also carries `modules`: what `list_modules` returns, so most conversations skip that call.                                                                                                                                                                  |
| Pinned tools: `search_tasks`, `get_task`, `create_task`, `update_task`, `search_documents`, `get_document`, `trace_lot`, `get_distribution_impact` | The tools agents reach for first stay listed natively (a tool opts in with `pinned: true`).                                                                                                                                                                                                             |
| `list_modules`                                                                                                                                     | Each module the connection can use: its **resources** and the names of its other tools (no schemas).                                                                                                                                                                                                    |
| `find_records(resource, filters?, workspace?)`                                                                                                     | Reusable read: lists or searches one resource (`items`, `suppliers`, `complaints`, `purchase_orders`, `stock_lots`, `management_reviews`, … about 80 of them). `filters` are checked against that resource's own filters; an unknown filter is refused with the accepted ones (never silently ignored). |
| `get_record(resource, id, options?, workspace?)`                                                                                                   | Reusable read: one record by id, code or reference (`FLR-001`, `CMP-2026-004`, a UUID). `options` are the resource's extra options (e.g. `batches` for a recipe).                                                                                                                                       |
| `describe_module(module)`                                                                                                                          | Full schemas for one module: each resource's filters and options, and every other tool with its description and arguments.                                                                                                                                                                              |
| `run_module_tool(name, args)`                                                                                                                      | Calls any of the connection's tools by name. `args` are checked strictly against that tool's schema, then the tool runs exactly as if it had been called directly (same handler, delete `confirm` guard, error shape and API checks). One `run_module_tool` call is one tool call for the rate limit.   |

The flow: `get_workspace_overview` → `find_records` / `get_record` to read → `describe_module` once per module the agent needs to write to or report from → `run_module_tool`.

Writes and specialist readers (reports, schedules, trends, plans) are not reusable and stay named tools. They are reached through `describe_module` and `run_module_tool`. Every `list_*` / `get_*` tool that is a plain list of records or one record by id is a resource instead (`resource: { name, op }` in its `define()`); `catalogue.test.ts` fails if one is added as a plain tool without being on its allow-list of specialist readers.

One gate decides what a connection is **shown**: module visibility, `requiresModules`, token actions and read-only scope. `tools/list`, `list_modules`, `describe_module`, the overview's `modules`, and the names and fields in an error all follow it, in both list modes. A hidden tool or resource gets the same `unknown_tool` / `not_found` answer as a misspelt name, and a malformed call to one never reveals its fields. Over HTTP the server registers every active module's tools and every token action's tools, so that calls reach the API, which checks module access and actions on every request. It reads the user's module access and token actions lazily, once per request, only when something is shown (`catalogue.ts`, `CallerAccess`). As a result, a describing call in a batch never changes what the batch's other calls do. Over stdio the access is read at startup and hidden tools aren't registered at all. Read-only scope always removes write tools entirely.

#### Listing every tool (`list=all`)

Add `?list=all` to the URL (stdio: `KNOTWORKING_MCP_LIST=all`) to list every tool natively, as before catalogue mode. `list_modules`, `find_records` and `get_record` are listed too; `describe_module` and `run_module_tool` are not. Use it for clients that handle large tool lists well (for example ones with their own tool search) or scripts that call tools by name. **Upgrading:** catalogue mode is the new default, so a client that called module tools by name (for example `list_items`) either adds `?list=all` or switches to `find_records` / `run_module_tool`.

#### Narrowing

- **Per connection, over HTTP:** add `?tools=read` (read-only tools only) and/or `?modules=bi,purchasing,items` (only those modules' tools; platform tools such as `get_workspace_overview` always stay) to the URL, e.g. `claude mcp add --transport http knotworking "http://localhost:4100/mcp?modules=bi,purchasing,items" --header "Authorization: Bearer knw_…"`. Both combine with `list=`.
- **stdio:** set `KNOTWORKING_MCP_TOOLS=read` and/or `KNOTWORKING_MCP_MODULES=bi,purchasing,items`.
- **Per token:** untick modules when creating the token. This also limits what the token may read, not just what is listed.

These choices only narrow:

- a module the token's user can't read is never offered;
- every call is still checked by the API;
- in read-only mode, write tools aren't registered, so they can't be called either (not even through `run_module_tool`).

An unknown module, `tools` or `list` value is refused, with a `400` over HTTP or an exit for stdio.

Measured with every module on and every token action on:

| Selection                                                         | `list=all` tools | tokens | catalogue tools | tokens |
| ----------------------------------------------------------------- | ---------------- | ------ | --------------- | ------ |
| everything                                                        | 286              | 97,000 | 15              | 4,100  |
| `tools=read`                                                      | 167              | 42,000 | 13              | 2,900  |
| `modules=bi,purchasing,items` (a dashboards and purchasing agent) | 48               | 17,500 | 7               | 1,200  |
| the same, `tools=read`                                            | 30               | 7,700  | 7               | 1,200  |

`catalogue.test.ts` keeps the default list under 8,000 tokens.

A dashboards agent needs write tools for `create_dashboard` and `create_analysis`, so give it modules rather than `tools=read`.

The listing itself is compacted: a `pattern` that only repeats a `format` (every uuid field had a 160-character regex) and `$schema` are left out, and the workspace parameter's explanation is in the server instructions once instead of on every tool. Calls are still validated against the full schemas. Together this saved about 20% of the full listing.

## 4. Tools

Every workspace-scoped tool takes an optional `workspace` slug (see `KNOTWORKING_DEFAULT_WORKSPACE`). Where a tool takes a team, state, label, member or project you can give its **name** (or team key, or email) instead of an id; the server resolves it from the workspace and answers with an `isError` result that lists the valid options when nothing (or more than one thing) matches. Tasks, documents and comments are addressed by the ids that the list tools return. Results are compact JSON text and list sizes are capped.

**Tools that appear only when allowed.** Eight tools exist because an owner or admin switched an action on under **Settings → API access**: `send_purchase_order`, `email_purchase_order` (the same `purchasing.send` switch), `close_purchase_order`, `cancel_purchase_order`, `record_stock_waste`, `adjust_stock`, `post_stocktake` and `cancel_production_batch`. They are marked `tokenAction` in the code and the tool list shows each only while its module is visible to the token's user **and** its action is enabled. The server reads `GET …/token-actions` for the default workspace (or the user's only workspace) next to the module list: once per `tools/list` over HTTP, once at startup over stdio (restart after a switch changes). If it can't tell (several workspaces and no default, or the read fails), the tools stay hidden. This only shapes the list: the API checks every call, so a call after the action was switched off is refused with `403 token_not_allowed` and a message naming the setting (`API tokens can't send purchase orders in this workspace unless an owner or admin allows "Send purchase orders" under Settings → API access`). The token's owner still needs the route's module level, and the actions are workspace-wide (no per-token allowlist yet). Attendance actions have no tools; integrations call the API for those.

**Dates and the workspace time zone.** Every date a tool takes or returns (`YYYY-MM-DD`: `ordered_on`, `received_on`, `from`/`to` ranges, due dates, `today` in due lists) is a calendar day in the **workspace's time zone** (an IANA name, default `Europe/London`, set by owners and admins in the app), and the API decides "today", what is due, whether a date is in the future and which week or month a record falls in by that zone, never by UTC or the agent's own clock. `get_workspace_overview` returns `workspace.timeZone` and `workspace.today` (today's date there); use that `today` rather than your own idea of the date. Timestamps (`checkedAt`, `createdAt`, …) are ISO instants, unaffected by the zone. Tokens can read the zone (`GET …/settings`) but never change it.

**Paging.** `list_tasks`, `search_tasks`, `list_projects`, `list_documents` and `list_comments` take `limit` (defaults unchanged) and `offset` (default 0) and return `total`, `offset`, `returned` and `hasMore`. `list_comments` without `offset` shows the _newest_ `limit` comments of a long thread (its `offset` says where that window starts); pass `offset: 0` to page forward from the oldest.

**Large workspaces.** The API's workspace snapshot (bootstrap) holds at most 5000 tasks, silently. The tools never rely on it for tasks: `get_task`, `update_task`, `list_comments` and `create_comment` address the task directly (`GET …/tasks/:id`), and the snapshot is used only to turn names into ids. `list_tasks` and `search_tasks` send `team`, `project`, `assignee` and a specific `state_type` to `GET …/tasks` (up to 500 matching tasks); other filters (`state` name, `open`, `none`) are applied to what was fetched, and with no API-side filter the snapshot is the source. When a source may have been cut off (the snapshot has exactly 5000 tasks, or the API returned 500) the result carries `truncated: true` and a `note`, and `total` is then only a lower bound: narrow the filters. `get_workspace_overview` reports `tasksTruncated` the same way.

Annotations follow the MCP hints: read tools are `readOnlyHint`; creates (and `log_time`, `start_timer`, `stop_timer`, `add_task_dependency`, `record_ccp_readings`) are non-destructive and non-idempotent (sending the same readings twice records them twice); `update_task`, `update_project`, `update_time_entry`, `update_document` and `restore_document_revision` are marked destructive because they overwrite fields (a replaced description or body is not recoverable through this server, except through version history for documents); `move_document` is non-destructive and idempotent; `set_demand`, `import_demand_csv`, `set_pack_units`, `copy_demand_forecast`, `import_items_csv`, `import_suppliers_csv`, `import_staff_csv` and `import_item_nutrition_csv` are destructive (they replace quantities) and idempotent (sending the same lines again changes nothing). The delete tools (`delete_task`, `delete_project`, `delete_document`, `delete_time_entry`, and `remove_task_dependency`) are `destructiveHint: true` and idempotent.

**Text:** descriptions, comments and document bodies are plain text, one paragraph per line (`textToDoc` / `docToPlainText` from `@knotworking/core`). Reading flattens headings, lists and links to lines of text. A table reads as one line per row with the cells separated by `|` (`Name | Status`); the header row is not marked, and merged cells, column widths and formatting inside cells are not shown. Uploaded images show as `[image: filename]` (there is no tool to fetch attachment bytes). Replacing a body with plain text loses all of that: headings, lists, links, marks and **tables** become ordinary paragraphs (a table you wrote back as `a | b` lines is just text, never a table again), which is why `update_document` has a safe `append` mode. `append` keeps every existing node, tables and images included, byte for byte and adds paragraphs after them.

**Mentions.** People write `@`-mentions of people, tasks and pages into documents and task descriptions (see [architecture.md](architecture.md#mentions-and-backlinks)). Reads flatten them to text from the label cached when they were written: `@Ada`, `[[Doc title]]` and `#Task title`, so a name or title may be stale or the target gone. `append` keeps mention nodes intact, like tables. Replacing a body with `content` turns them into plain text (`@Ada` stays text, with no link and no notification), so prefer `append`. Typing `@Ada` in text you write does not create a mention. A page's backlinks (who mentions it) come from `get_document_backlinks` and `get_task_backlinks` (backed by `GET …/documents/:id/backlinks` and `…/tasks/:id/backlinks`).

**Time reports.** `get_time_report` is read-only and works with `read` tokens. Like every time-entry route it shows the whole workspace's time (every member can already read everyone's entries), narrowed by the optional `project`, `team` and `person` filters; it never includes email addresses. Estimates are compared only on tasks that have one (`varianceMinutes`), and the estimate belongs to the whole task while the report sees only the dates asked for, so ask for a range that covers the work. There is no CSV tool: agents get the same numbers as JSON (`GET …/time-report.csv` also accepts a token for scripts).

**Document writes.** `append` reads the document, adds the text and saves with `expectedUpdatedAt` set to the `updatedAt` it read. If someone saved in between, the API answers `409 document_conflict` and writes nothing; the tool re-reads and retries, up to 3 attempts, then returns an `isError` result (`document_conflict`, "being edited concurrently", nothing changed). Replacing with `content` rejects empty or whitespace-only text (`invalid_input`), so one call can't wipe a document. By default it does not check for concurrent edits: it overwrites (last write wins). To guard a replace or a rename, pass `expected_updated_at` (the `updatedAt` that `get_document` returned, or the previous `update_document` result): the tool sends it as `expectedUpdatedAt`, and if the page was changed in the meantime (for example by a person in the web editor) nothing is written and the result is an `isError` `document_conflict` that says to re-read with `get_document`, merge and retry; it is never retried automatically. `expected_updated_at` is refused together with `append`, which always works on the latest content. Renaming (`title` only) never touches the body. Every `update_document` write that changes the title or body is also saved to the document's version history (author: the token's user, folded into one revision per 10-minute window like any autosave), so a person can see and restore what an agent changed from the doc's History panel (see [architecture.md](architecture.md#document-version-history)). Agents can do the same with `list_document_revisions`, `get_document_revision` and `restore_document_revision`: a restore replaces only the title and body (parent, team, project and cover stay), first saves the current state as a `before-restore` revision, so it can be undone by restoring that one, and with `expected_updated_at` it refuses (`document_conflict`, nothing changes) when the page was edited after you last read it. History keeps at most the latest 100 revisions per document, and a deleted document's history is gone with it. The web editor guards its own saves the same way, so an agent's write makes an open editor show a "changed by someone else" prompt on its next save instead of being overwritten (see [architecture.md](architecture.md#document-edits-and-expectedupdatedat)).

**Deleting.** The `delete_*` tools are destructive and the server says so (`destructiveHint`, a description that spells out what is lost, and the server instructions). Each of the four that remove data refuses to run, before any API call, unless the agent passes `confirm: true` (`confirmation_required`, "Nothing was deleted"), so a vague instruction or a mistaken call cannot delete by accident. What the API actually does: `delete_task`, `delete_project`, `delete_document` and `delete_time_entry` are **soft deletes** (the row stays in the database with a `deletedAt` timestamp, and a tombstone goes into the sync log), but nothing in the API or the web app can restore them, so treat them as permanent. A task's dependencies are removed with it, its subtasks are kept, and its comments, time entries and attachments become hidden with it; a project's tasks and documents are kept and detached; a document takes **all of its sub-pages** with it and its history becomes unreachable. `remove_task_dependency` only unlinks two tasks and needs no confirmation. There are no tools to delete comments or attachments.

**Time tracking.** Time entries belong to a person. `log_time`, `start_timer` and `stop_timer` always act for the token's user (the tools have no user argument, although the API lets owners and admins log time for others). `update_time_entry` and `delete_time_entry` follow the API's rule: your own entries, or anyone's if the token's user is an owner or admin; otherwise `403 forbidden`. A person has one running timer per workspace across all tasks. Entries are 1 minute to 24 hours (log several for longer work); `date` is a calendar day, and when omitted the API uses today in the workspace's time zone. Durations are read with `parseDuration` from `@knotworking/core` (`90`, `1:30`, `1h 30m`, `1h30`, `1.5h`, `2h`, `45m`, `45 min`); an unreadable one is an `invalid_input` error that lists the accepted forms. `estimate_minutes` on `create_task` / `update_task` takes the same forms (up to 1000 hours; `null` clears it).

**Dependencies.** `add_task_dependency` and `remove_task_dependency` take task ids or exact titles; a title is looked up in the workspace snapshot, which holds at most 5000 tasks, so use ids in very large workspaces. `get_task` lists `blockedBy` and `blocking` from the snapshot (all dependencies are included, but a related task beyond the snapshot's task cap shows a null title and state).

**Attachments.** `list_task_attachments` is read-only metadata (id, filename, content type, size, uploader, date). There is deliberately no upload tool and no tool that returns file contents (the one exception is `get_attachment_link`, which returns only a short-lived signed URL for the person to open): there is no safe design yet for moving binary data through MCP (size limits, base64 in the model's context, untrusted file types, injection through file contents). Images inside documents read as `[image: filename]` as before. Files on module records (certificates, specification sheets, photos, reply letters) are listed the same way by the `list_<module>_record_attachments` tools: metadata only. `get_attachment_link` gives a short-lived signed link to a listed file; there is no upload, replace or delete, and no tool that returns file contents.

**Not included on purpose.**

- **Labels, teams and workflow states** (create, edit, archive, delete). The API routes are admin-only and refuse tokens (`token_not_allowed`), whatever the owner's role, so a token-based tool could not work and must not be added. Their names are still readable through `get_workspace_overview`, and the tools accept them.
- **Members, invitations, roles and password resets**, API-token management, and **calendars and meetings** (including writes): admin or personal, token-forbidden.
- **File upload and download** (see above).
- **Comment edit and delete, notifications and their preferences, project time totals** (`GET …/projects/:id/time`, which `get_time_report` covers), the sync log and event stream: the routes are token-accessible but no tool wraps them yet.
- **Logging time for other people**, even where the API would allow it.
- **Hard delete or undelete of anything**: nothing here is hard-deleted, and nothing can be restored either (see Deleting).
- **Food safety records signed by people**: reviewing (approving or rejecting) CCP readings, recording cleaning, verification and calibration, correcting a reading, a cleaning record or a calibration record, signing off a day's monitoring, approving a HACCP plan, reviewing its hazard analysis, signing off several plans at once and closing a corrective action. Agents may enter CCP readings (`record_ccp_readings`; any token with haccp write may post them to the API) to make data entry quicker, but those readings are `source: api` and `pending` until a person with manage access approves or rejects them in the app (`POST …/haccp/logs/:id/review` and the bulk `POST …/haccp/logs/review` refuse tokens). There is no review tool: an agent never approves its own readings.

## 5. Security

- **Scopes.** A `read` token can only `GET`; writes fail with `token_read_only`. A `write` token acts as its owner, so the owner's workspace role still applies (a guest's write token is still read-only). Use `read` tokens unless the agent must change things, give each agent its own token, and set `expiresInDays`.
- **No admin or personal data.** The API refuses tokens on admin routes, on `/v1/calendar/*`, the combined calendar view, calendar import and meeting create/update/cancel/notes (`token_not_allowed`), whatever the owner's role. Meetings are written through the owner's connected calendar, so agents can read workspace meetings but not change them. The MCP server also exposes no tool for them. Its delete tools are limited to tasks, projects, documents and time entries, each behind `confirm: true`, plus unlinking a dependency; it cannot delete labels, teams, members, comments or attachments.
- **Revoking.** Deleting a token (the **Revoke** button on the API tokens page, or `DELETE /api/v1/me/api-tokens/:id`) or deleting the user stops it immediately (`401`). Event streams (`/events`) that were opened with the token are only checked periodically, so they end shortly after the revocation rather than at that instant (the same holds when the token expires or its owner is deactivated). A token also stops working while its owner has no active workspace membership, and works again if they are reactivated (deactivating someone from only one of several workspaces does not stop it). Resetting or changing a password revokes all of that user's live tokens, because a leaked credential may be what prompted it; create new ones afterwards. If an account may have been exposed without a password change, revoke the tokens yourself. The MCP server stores nothing, so there is nothing to clean up on its side.
- **Untrusted content.** Task text, comments and documents were written by other people, and some of it may be written to manipulate an agent ("ignore your instructions and…"). The server's instructions and the read tools' descriptions tell agents to treat workspace text as data, not instructions. That reduces the risk but cannot remove it: a write token lets an agent that was tricked change anything its owner can, so prefer `read` tokens for agents that process other people's text, and review what write-capable agents do.
- **Token handling.** HTTP mode only forwards the bearer token to `KNOTWORKING_API_URL`. It is never logged or stored, and it is stripped from any error text returned to the agent. Only `knw_` tokens are accepted: a browser session token is rejected with `401`. Use HTTPS in front of the server (the compose setup with `DOMAIN` does) so tokens don't cross the network in clear text.
- **Reaching it by another address.** Connecting through an IP or hostname that isn't `APP_URL` or in `TRUSTED_ORIGINS` (for example `http://192.168.1.20/mcp` on a LAN) gets `403 Invalid Host`. Add that hostname to `MCP_ALLOWED_HOSTS`.
- **HTTP hardening.** The `Host` and `Origin` headers must match `MCP_ALLOWED_HOSTS` (protection against DNS rebinding from a web page); there is no CORS, so browsers can't call the server cross-origin; request bodies are limited by `MCP_MAX_BODY_BYTES`; only `POST /mcp` is served.
- **Limit amplification.** One HTTP request can carry a JSON-RPC batch and each tool call can fan out into several API requests, so the server caps all three. Batches larger than `MCP_MAX_BATCH` (default 10) are refused with `400` and a JSON-RPC error before any work starts (the MCP SDK alone would accept 100). Within one HTTP request the workspace snapshot (per workspace slug) and `/v1/me` are fetched once and shared by the batch's tool calls, and forgotten when a write tool in that request finishes; that memo belongs to the request and its token and is never shared. Each token is limited to `MCP_RATE_LIMIT_PER_MINUTE` (default 120) `tools/call`s a minute, counted per call inside batches (`initialize` and `tools/list` are free): beyond that the answer is `429` with `Retry-After` and a JSON-RPC error. Counters live in memory, keyed by a SHA-256 hash of the token (the token itself is never stored), idle entries are dropped and the table has a hard size cap, so a restart resets them and several MCP replicas each count separately. The API's own limits still apply behind it.
- **Errors.** API failures come back as tool results with `isError: true` and `{"error":{"code","message","status"}}` using the API's code (`unauthenticated`, `token_read_only`, `not_found`, `invalid_input`, …), plus `api_unreachable`, `ambiguous` and `internal_error` from the MCP server itself. They are never protocol errors, so the agent can read them and adapt.
- **Rate limits (two layers).** The MCP server's limit above is **per MCP process**: its counters are in memory, so a restart resets them and running N replicas allows N times `MCP_RATE_LIMIT_PER_MINUTE` per token. The API enforces its own per-token limits as well (separate budgets per minute for reads and for writes, counted per API process, so the same restart and N-replica caveats apply). They hold for direct API use with a token too, not only through MCP: over budget the API answers `429 rate_limited` with a `Retry-After` header, and the MCP tools surface that as an `isError` result. Sign-in sessions (the web app) are not subject to the token limits. The API limits default to 600 reads and 120 writes per token per minute and are tuned with `API_TOKEN_READ_LIMIT_PER_MINUTE` and `API_TOKEN_WRITE_LIMIT_PER_MINUTE` (`0` turns a budget off); see `.env.example`. Both layers are brakes against runaway agents, not exact distributed quotas: if an agent hits `429`, have it back off for `Retry-After` seconds.
- Writes go through the normal API, so they land in the sync log and show up live for everyone else, attributed to the token's owner. Task comments and assignments can trigger the usual notification emails.

## 6. Development

```bash
pnpm --filter @knotworking/mcp test         # unit tests + end-to-end MCP client tests against a fake API
pnpm --filter @knotworking/mcp typecheck
pnpm --filter @knotworking/mcp build        # dist/http.js and dist/stdio.js, fully bundled
```

- `src/tools.ts` creates the server and defines the platform tools (`list_workspaces`, `get_workspace_overview`); every module's tools are in `src/tools/<module>.ts` (`tasks.ts`, `docs.ts`, `time.ts`, `items.ts`, …), with helpers shared by the workspace tools in `src/tools/shared.ts`. `src/model.ts` resolves names to ids from the workspace bootstrap (one `GET …/bootstrap` per tool call; in HTTP mode a batch shares it through the per-request memo in `src/api.ts`, stdio memoizes nothing), `src/app.ts` is the Hono HTTP app (batch cap, rate limit from `src/rate-limit.ts`) and `src/http.ts` / `src/stdio.ts` are the entries.
- Tests run the real tool set against `src/testing/fake-api.ts`, an in-memory stand-in that enforces the real request schemas from `@knotworking/core` and token scopes. It also mimics the server's `expectedUpdatedAt` / `409 document_conflict` contract, `GET …/tasks` filters and the 5000-task bootstrap cap, plus the real rules for dependencies (`relation_exists` / `relation_cycle`), time entries (own entries only unless `hooks.timeActorIsAdmin`, one running timer), project and document deletes, revisions and backlinks, with hooks (`hooks.beforeDocumentPatch`, `seedTasks`) for simulating concurrent edits and big workspaces. Tests cover name resolution, text conversion, error mapping, safe document writes, paging and truncation, the HTTP 400/401/403/405/413/429 paths (batch cap, rate limit with a fake clock, memoization counted by fake-API hits) and a full MCP client session (initialize, `tools/list`, `tools/call`).
- The package never imports `@knotworking/db` or server code (a test enforces it). The bundle includes every dependency, so unlike the API image there is no `runtimeExternals` list and the Docker target needs no `npm install`. If a dependency ever has to stay external, add that list and keep it in sync as `apps/server` does.
- A new tool is: a `define(…)` call in its module's `src/tools/<module>.ts` with precise annotations, a row in the table above, and a test.

Live incidents: `list_incident_cases` and `get_incident_case` read Quality cases only when Quality, Despatch and Production are all readable. Distribution snapshots contain historical customer contact details. Evidence includes superseded entries and corrections; quantities are off-site dispositions, not stock receipts. There are no tools for containment, evidence attestation, hold release or signed closure. No incident route sends messages.

Distribution operations: `list_customer_delivery_sites` reads a customer's delivery-site register; `get_despatch_operations` reads handling units/SSCCs, signed operations history, current and superseded proof and physical return receipts. `draft_despatch` accepts `deliverySiteId`. Agents may prepare a draft; allocation, packing, load checks, confirmation, delivery proof, return receipt and corrections remain signed-in managers' actions, with no MCP sign-off tools. Distribution impact follows physical return lot links as well as net production. A physical receipt is distinct from an off-site recovery/return report; do not sum them without reconciliation.

Food authenticity: `list_authenticity_assessments` and `get_authenticity_assessment` read Quality's recorded scopes, current/draft/prior reviews, controls and evidence. `create_authenticity_draft`, `start_authenticity_review`, `save_authenticity_draft` and `raise_authenticity_review_trigger` prepare work; retain command ids on retries, and use a fresh `expectedUpdatedAt` for reviewed-version mutations. Full draft replacement must retain evidence/controls intended to remain. Linked samples need Testing read permission when linking and are source references only. Approval, control verification, correction and archive are person-only in the app. List results do not establish full raw-material coverage or supplier/lot release. Overdue/failure flags and unresolved triggers must be surfaced even after a passing recheck. Nothing fetches external intelligence or sends a message automatically. The authenticity tools are listed only when the caller can read Items.

### General business operations

- `list_purchase_requests` and `get_purchase_request` read requests within the person's purchase-request access. The list supports requester, assigned and manager views, a status filter and cursor paging.
- `list_service_quotes` and `get_service_quote` read customer service quotes with project links, approved billing and decision history. They require Client services access. Quote and delivery decisions are made by signed-in managers in the app.

### Sales (3.4.1)

Sales tools require `module: sales` (Customers and Items are dependencies):

- `list_sales_documents`: paginated quotes/orders, filtered by kind/status/customer UUID.
- `get_sales_document`: current snapshot, or paginated retained revisions with `history: true`.
- `draft_sales_document`: create with `salesCreateSchema` or replace a draft with `salesSaveSchema`; command UUID and reviewed revision make retries/stale writes explicit. Never confirms or amends a signed commitment.
- `list_sales_prices`: paginated current/archived customer price agreements.
- `get_sales_commitments`: confirmed sales only, by daily delivery date, ordered/outstanding base quantities, explicit `forecastIncluded: false`. These records are not automatically published into weekly Demand/Production planning.

Issuing/converting quotes, confirming/amending/cancelling orders, agreeing/archiving prices and linking/correcting deliveries remain signed-in manager actions with no MCP sign-off tools. Sales data is commercially restricted. Future adapters use the versioned Sales HTTP contract, stable UUIDs, command receipts and workspace/system external mappings; no verified external sales or accounting connection is delivered by this milestone.

### Health, safety and environment (3.4.3)

HSE tools require HSE and Training access. The contractor permit tools also require Assets read access.

- `list_hse_registers`: paginated scopes, kind/status filters, review/check dates and unresolved failures. Coverage is recorded scopes, not a site-wide all-clear.
- `get_hse_record`: current approved/draft content, paginated retained versions or verification/measurement entries.
- `draft_hse_register`: prepare/create or save an existing review draft with a durable command ID and reviewed revision. Referenced Tasks need additional Tasks read access on linking.
- `list_hse_permits`, `get_hse_permit`: paginated permit status/expiry, retained issue evidence and signed decision history.
- `draft_hse_permit`: prepare work against an existing asset of the register (Assets), HSE assessments, contractor competence and worker training. Optional visitor references additionally need Attendance read access.
- `report_hse_near_miss`: report a near miss, unsafe condition, dangerous occurrence or environmental incident in which nobody was hurt. Only the reference comes back; restricted incidents themselves stay unavailable to tools.
- `list_hse_record_attachments`: existing attachment listing for HSE registers, checks and permits; no upload/delete/sign-off powers.

Approval, archive, verification/correction, permit issue/suspend/resume/cancel and return to service require a signed-in person and have no MCP tools. `hse_incidents` is a separate restricted permission: **no private incident tools**, including read tools (`report_hse_near_miss` only creates a report and returns its reference). Its routes refuse every API token, and its data/metadata never enter workspace sync. Personal incident files remain in the site's approved restricted store, referenced from the private investigation rather than general HSE attachments. No tool submits statutory/environmental reports or actuates equipment.

Accounting connection setup and mapping reviews are administrator actions by signed-in people. All `/accounting/*` configuration routes refuse personal API tokens; no MCP tools expose credentials, financial configuration or sign-off. The optional Accounting module remains off unless the environment explicitly enables it.

Workforce adds `get_workforce_availability` (`module: workforce`): a paged date-only unavailable view, bounded to a 366-day window. It includes no illness/leave type, notes, private record IDs or reviewers, and reports source availability explicitly. Personal requests and all Private HR routes require a person's session, so there are no MCP tools for them. `get_rota` (31-day window: shifts, rostered people, roles, agencies and a date-only `unavailable` flag) and `get_staffing_check` (requirements, who counts, shortfalls and reasons; training detail only for Training readers) are read-only and also declare `module: workforce`. See [Workforce delivery](workforce.md).
